# Возобновляемая обработка больших комплектов

## Выполнение

Создание фонового аудита и намерения запустить подготовку выполняются одной
транзакцией PostgreSQL. Таблица `task_outbox` хранит доставку, попытки и срок
владения заданием. Сервис `task-relay` раз в 5 секунд отправляет сохранённые
задания и восстанавливает просроченное выполнение. Повторное сообщение с тем же
идентификатором и токеном не выполняет операцию второй раз.

Подготовка делает контрольные остановки примерно каждые 120 секунд, после
сохранения страницы или позиции. Это не жёсткий лимит на комплект: следующая
задача продолжает подготовку. Уже разобранный ВОР, подготовленные позиции и
успешно извлечённые страницы используются повторно. PDF открываются по мере
необходимости; все документы одновременно в память не загружаются.

Мягкий таймаут Celery больше не считается обычной ошибкой позиции внутри
PDF/OCR-кода. Он передаётся механизму повторных попыток. Жёсткое завершение
процесса обнаруживается по истечении срока владения: таймаут задачи + 60 секунд.
После трёх неудачных исполнений аудит переходит в `failed`, причина сохраняется
в `runs.config.execution_error`. Успешные контрольные остановки не расходуют
попытки. Проверка не остаётся бесконечно в `running` из-за одного погибшего
дочернего процесса при живом родительском воркере.

Доставка в Redis повторяется через 60 секунд, если задачу ещё не забрал воркер.
До начала выполнения сохраняется тот же токен доставки. Число одновременно
отправленных/выполняющихся заданий ограничивается примерно 32; окончательная
нагрузка задаётся `AUDIT_PDF_CONCURRENCY` и `AUDIT_LLM_CONCURRENCY`.

## Хранение и поиск

Снимок по-прежнему содержит полный корпус, исходные номера страниц и
проверяемый `corpus_id`. Физически он хранится как небольшой манифест и общие
неизменяемые страницы, адресуемые по хешу. При изменении доказательств для
позиции записываются изменённые страницы и манифест. Старые монолитные снимки
продолжают читаться.

Контекст всех позиций ВОР хранится один раз; в заданиях остаётся ссылка.
Проверки состояния запуска больше не загружают все накопленные результаты.
Поиск использует прежнее ранжирование и весь текст документа. Токены страниц
переиспользуются; индекс ранжирования подготовки пересоздаётся при изменении
текста после OCR. Кеш проверенных байтов страниц и кеш токенов ограничены
32 МиБ каждый на процесс. Кеш байтов не отдаёт общие изменяемые JSON-объекты.

Полнота аудита, бюджеты запросов к модели и правила подтверждения доказательств
не сокращены. Скорость всей проверки зависит также от OCR, таблиц и провайдера
модели; ускорение операций со снимками не равно ускорению всего аудита.

## Финализация

Условие проверяется под блокировкой строки запуска: подготовка завершена,
число заданий соответствует ожидаемому числу позиций, все позиции завершены,
нет незавершённых долговечных LLM-заданий. Намерение собрать отчёт сохраняется
в той же транзакции, что и `finalize_chained`. Сбой Redis после этого не теряет
финализацию. Повторная сборка заменяет артефакт того же типа.

## Обновление Ubuntu-сервера

Для локального стенда Windows используется отдельная конфигурация:

```powershell
cd D:\VOR\smeta-checker-dev
docker compose -p smeta-checker-local --env-file .env.local -f compose.yaml -f compose.local.yaml up -d
```

Интерфейс: `http://localhost:3000`. Логин и пароль находятся в игнорируемом
`.env.local` в полях `WORKSPACE_LOGIN` и `WORKSPACE_PASSWORD`. Локальный стенд
использует отдельные Docker volumes; загруженные документы и результаты
сохраняются между перезапусками. Для просмотра ошибок:

```powershell
docker compose -p smeta-checker-local --env-file .env.local -f compose.yaml -f compose.local.yaml logs --tail 100 api worker-pdf worker-llm task-relay
```

Сначала штатно сделайте резервную копию БД и blobs. Обновление требует миграции
`0006_task_outbox` и нового сервиса `task-relay`. Обновляйте API и воркеры одним
комплектом; оставлять старый API с новыми воркерами не следует.

Пример последовательности из каталога проекта при уже работающих db/redis:

```bash
docker compose stop api worker-pdf worker-llm task-relay
docker compose build api migrate worker-pdf worker-llm task-relay
docker compose run --rm migrate
docker compose up -d api worker-pdf worker-llm task-relay
```

При недоступном relay сохранённые задания остаются в БД. Следите за его
healthcheck и логами, как и за другими обязательными сервисами.

## Возобновление старого зависшего аудита

Для запуска, застрявшего до обновления, остановите старые воркеры и relay.
После миграции выполните, подставив UUID запуска:

```bash
docker compose run --rm --no-deps api python -m scripts.resume_audit RUN_UUID
docker compose up -d worker-pdf worker-llm task-relay
```

Команда сохраняет завершённые позиции, возвращает незавершённые в очередь и
повторно планирует подготовку. Завершённые и отменённые аудиты она не меняет.
Активный срок владения новым заданием команда не отбирает: после остановки
воркеров необходимо дождаться его истечения. Для новых запусков с outbox
восстановление после потери процесса происходит автоматически.

## Проверки

`backend/tests/test_durable_tasks.py` проверяет таймаут и продолжение на другом
воркере, повторную доставку, потерю дочернего процесса, отказ брокера,
ограничение повторных попыток, конкурентную финализацию, возобновление с
сохранением результатов и путь prepare → audit → Word с синтетической моделью.
Модель в этих проверках не вызывается.

Проверка 26.10.2026: Python 3.14.9, отдельный PostgreSQL 16.10 на Windows.
После исправления структурных таблиц полный backend-прогон: 589 тестов прошли,
1 пропущен и 3 упали из-за отсутствующего Tesseract в локальном Windows PATH.
Эти три падения воспроизводились и на исходном HEAD. Все 11 прежних падений
тестов таблиц устранены. Ruff и Pyright прошли. Локальный Docker-стек запущен;
извлечение четырёх колонок и количества 75 м из реальной страницы ПД проверено
также внутри API-контейнера, без обращения к модели и изменения сохранённых
результатов аудита.

## Структурные таблицы и правила сверки

Физическая сетка таблицы, заголовки и адреса ячеек сохраняются отдельно от
плоского текста, в том числе в общих постраничных снимках. При выборе фрагмента
строка определяется по наименованию работы, а не по ожидаемому количеству.
Заголовки и целая строка остаются в пределах лимита цитаты. Если рамка чертежа
мешает разбору сетки, повторное извлечение ограничивается областью строк;
результат принимается только при корректной структуре и сохранении всех слов
в этой области. Версия кэша таблиц изменена, старые повреждённые сетки не
используются при подготовке новых проверок.

Парные значения `шт./т | 114/23,53` связываются с единицами по порядку.
Часть выбирается по единице ВОР, а не по совпадению числа. Характеристика
`1680 шт./км` в наименовании не подменяет количество из отдельной колонки.
Служебные номера A и идентификаторы J не сравниваются с ПД. Отсутствие формулы
не является ошибкой; явно заданное количество проверяется напрямую, а
заполненная формула по-прежнему проверяется на арифметические ошибки.

Сохранённые результаты завершённых проверок не пересчитываются автоматически.
Для применения новых правил запускается новая проверка с теми же документами.

Синтетический замер хранения: 150 текстовых страниц, 20 позиционных снимков,
по одной изменённой таблице. Исходная реализация: сохранение 1,113 с,
загрузка 2,117 с, объём 1 635 907 байт. Новая реализация: сохранение 0,402 с,
загрузка 0,795 с, объём 309 764 байт. Это примерно 2,7 раза по суммарному
времени операций со снимками и 5,3 раза по объёму. Замер не включает OCR и
время ответов провайдера модели и не предсказывает длительность всего аудита.
