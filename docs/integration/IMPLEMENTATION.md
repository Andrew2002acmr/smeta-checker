# Реализованное подключение Nuxt к smeta-checker

19 октября 2026. Ветка `integration/nuxt-review`, база — `dev` на `7d60864`.

## Что работает

Наш интерфейс КДФП перенесён в `frontend/` и обращается к настоящему API smeta-checker через Nitro. Старый Streamlit и прежние REST-маршруты сохраняют совместимость.

- Создание/выбор проекта; загрузка XLSX/CSV/PDF; список версий; выбор одной версии каждого документа; повторное использование одинаковых байтов.
- Предварительная проверка ссылок ВОР на PDF. Проблемы показаны до аудита; запуск при неполных привязках требует явного выбора пользователя.
- Отдельный audit run для каждой ВОР, стадии подготовки/проверки/финализации, реальные счётчики position jobs. При неизвестном общем числе позиций процент не выдумывается.
- История сохранённых аудитов, фильтры/поиск/пагинация строк, Excel/Word, восстановление выбранной позиции по URL после reload.
- Исходный лист и ячейки XLSX, окно таблицы, точная версия PDF, PDF.js, физическая/печатная страницы, дерево разделов и поиск по PDF.
- Цитаты с привязкой к версии PDF. Подсветка только при однозначном совпадении в нативном текстовом слое; для неустановленных координат остаётся честное сообщение и просмотр страницы.
- Проверка оформления выбранного листа XLSX через существующий `vor_rules.py`, отдельно от LLM.

## Изменения на сервере

`workspace_models.py`, `workspace_api.py`, `workspace_service.py` добавляют типизированные контракты, маршруты и представление сохранённых результатов. Пользовательские статусы/действия строятся существующим `audit_reports.build_user_report`; правила не копируются в TypeScript. `done` у запуска не выдаётся за отсутствие замечаний.

Новый run сохраняет снимок `position_inputs` в config с исходными версиями. У результата есть стабильный `(run_id, position_index)`; Repository возвращает индексы отдельно от JSON. Повторная загрузка/другая версия ВОР не меняет прежний аудит. Для старых запусков вход восстанавливается из их неизменяемой версии ВОР.

Парсер читает несколько рабочих листов XLSX и сохраняет исходную строку/столбцы до фильтрации и переиндексации. Строки-продолжения остаются частью соответствующей позиции. Сохранение результатов финализации больше не теряет `found_page` и `volume_calculation`.

При preflight/старте проверяется принадлежность версий проекту. Нельзя передать несколько версий PDF с одним именем: раньше словарь PDF мог молча перезаписать одну из них. Загрузка читает не более лимита + 1 байт перед проверкой размера. Выдача оригиналов поддерживает Range/206/416 и ETag.

Исправлен Windows `file://C:\...`: прежде `urlparse` принимал путь за authority, и fallback мог записать blobs в текущий каталог. Теперь и такой путь, и нормальный `Path.as_uri()`, и `file://./...` разрешаются в указанный каталог.

Новые поля снимка используют существующий JSON config; миграция схемы БД не требуется.

## Запуск и данные

**Рабочее приложение:** http://127.0.0.1:3010/, настоящий API — loopback 8100. PostgreSQL `smeta-workspace-db`, loopback 55433, постоянный volume `smeta-workspace-data`. Для перезапуска: `docker start smeta-workspace-db`, затем `./start-workspace.ps1`.

Секреты сгенерированы только в игнорируемом `.env`; frontend получает API-токен только в серверном окружении. Для настоящей проверки нужно заполнить `YANDEX_CLOUD_API_KEY` и `YANDEX_CLOUD_FOLDER` и перезапустить launcher. Пока они пустые, запуск отвечает `llm_not_configured`; загрузка, история и оформление работают. Рабочий entry point не содержит переключателя на подменные ответы модели.

**Синтетический испытательный стенд:** использовал loopback 3016/8116 и отдельную БД `smeta_test_ui`; после испытаний временные API/UI остановлены. Только `tests/workspace_server.py` подключает тестовый LLM-клиент. Названия проектов явно содержат «Синтетический». Это не результат проверки настоящего комплекта.

Существующий стенд `document-intelligence` и его данные не переключались и не переносились в новую БД. Проверено сохранение SHA всех 20 локальных файлов, использованных как исходная копия интерфейса/сервисов. Миграция пользовательской истории остаётся отдельным действием.

## Границы версии

- Подключены этапы 1–2 плана и просмотр источников из этапа 3. Полный перенос ONLYOFFICE, save receipts, редакторских ревизий, восстановления и PDF-заметок ещё не выполнен. В новом интерфейсе нет кнопок, выдающих эти действия за подключённые.
- Наш собственный движок подробной сверки D/E/проектных условий не переносился в smeta-checker. Сохраняется предметная логика этого backend; равенство результатов двух разных движков не заявляется.
- Не проводились живые обращения к Yandex, повторный OCR настоящих комплектов и оценка качества модели на большом корпусе. Тестовый прогон доказывает работоспособность интеграции.
- Nitro остаётся локальным входом с loopback/Host/same-origin/HttpOnly-сессией. Публичный сервер с пользовательскими ролями требует отдельной настройки доступа; удаление локальной проверки не заменяет её.

## Исправления истории и прогресса, 19.10.2026

Рабочий API перестал отвечать во время подготовки первой из 18 позиций: запрос списка проектов не завершился за 45 секунд, в PostgreSQL осталась одна задача `pdf/running`. Обработка PDF выполнялась в потоке самого HTTP-процесса; тяжёлый native parser способен удерживать GIL и останавливать обслуживание запросов.

- Production fallback теперь запускает `scripts.audit_worker` отдельным процессом. Он читает неизменные исходные версии из хранилища и использует прежний pipeline. Настройки передаются через stdin, без секретов в аргументах или дополнительных файлах. Инъекция тестового клиента и Celery-путь сохранены. Windows launcher завершает всё принадлежащее ему дерево процессов, включая PDF worker.
- История и progress используют один SQL-запрос метаданных и сгруппированных счётчиков. Пагинация выполняется в БД. JSON результатов, evidence, payload задач и полные снимки позиций для этих запросов больше не загружаются.
- Этап подготовки определяется по PDF-очереди и завершению prepare, а не по наличию любой задачи. До проверки позиций и при сборке отчётов показан неопределённый прогресс с описанием этапа; во время аудита — процент и количество выполняемых/ожидающих задач.
- Опрос автоматически восстанавливается после ошибки сети; GET ограничен 15 секундами ожидания. История обновляет выполняющиеся проверки, сохраняет индикатор до получения списка запусков и корректно обрабатывает пустой список проектов.

Зависший запуск `f81d5612-33a2-4f08-8608-0e1aa658f539` сохранён со статусом `failed` и причиной прерывания в config. Документы не изменены. Повторные обращения к модели для проверки исправлений не запускались.

После обновления рабочие API-запросы: проекты — 49 мс, история — 23 мс, прогресс — 33 мс (одиночные локальные измерения, не нагрузочный тест).

Проверки: **229 passed, 1 skipped** в Python, **3 unit** и **6 Playwright**. Новые регрессии проверяют отсутствие тяжёлых чтений истории/progress, SQL-пагинацию, этапы подготовки/аудита/финализации, реальный отдельный процесс без запросов к модели, загрузку/пустую историю и переход подготовки → ошибка 503 → 50% → сохранённые результаты. TypeScript, Ruff, Pyright, lint, форматирование и production build прошли. Журналы: `.audit_cache/progress-regressions.log`, `progress-e2e.log`, `progress-build.log`.

### Повторное зависание: фактическая причина в PDF extractor

Для запуска `874f5082-24e3-4efd-b4e7-596a1510759d` снят стек живого worker через py-spy. Он находился в `pymupdf.layout` / `BoxRFDGNN.predict` / `page_get_textpage` внутри `pymupdf4llm.to_markdown`. API после изоляции работал, но сам parser не продвигался. Поэтому прежняя проверка исправления HTTP-блокировки не доказывала завершение подготовки этого PDF.

Исходный PDF содержит 303 страницы, 78 781 067 байт. Обнаружены две независимые дорогие операции: нейросетевой анализ Layout и повторное сканирование всех страниц для определения шрифтов заголовков при каждом single-page вызове legacy Markdown. Теперь явно выбран deterministic RAG extractor, `hdr_info=False` отключает повторный полный проход, HTML-таблицы сохранены. Параметры отражены в ключе кэша.

Дополнительно ограничено число векторных объектов страницы: свыше 5000 путей извлекается доступный native text, сложный анализ колонок и таблиц пропускается, а reading error направляет такую страницу на ручную проверку. Неполный анализ не выдаётся за подтверждение. Это потребовалось, поскольку на страницах 282–283 около 40 тысяч векторных элементов и обычный анализ колонок также зависал.

Реальный локальный прогон нового `PDFTextSource` завершил все **303 страницы за 91,14 секунды**. Для ручной проверки отмечены страницы **76, 282, 283, 293, 294, 295, 297, 298, 300**. Этот прогон не обращался к LLM и не подтверждает качество итогового аудита. Счётчик подготовленных страниц теперь сохраняется в БД и отображается в UI; прогресс по страницам отделён от прогресса позиций.

Supervisor следит за изменением страниц/счётчиков задач и завершает всё дерево worker при отсутствии прогресса дольше `AUDIT_TASK_TIME_LIMIT` (по умолчанию 600 секунд). Длина нормально продвигающегося аудита этим лимитом не ограничивается. Тест отдельно запускает зависший дочерний процесс и проверяет его остановку по timeout. Playwright проверяет подготовку 151/303 → 503 → аудит 50% → результаты; все шесть браузерных сценариев прошли, также прошли три unit-теста, typecheck, Ruff, Pyright, проверка контрактов и production build.

Заключительная полная регрессия: **252 passed, 1 skipped, 67 subtests passed**. Журналы: `.audit_cache/parser-complete.log`, `parser-e2e.log`, `parser-build.log`. Рабочие API и UI после перезапуска отвечают HTTP 200.
