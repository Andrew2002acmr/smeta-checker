# Запуск smeta-checker в Docker

Инструкция описывает подготовку нормативных данных, настройку и запуск
интерфейса, API, PostgreSQL, Redis и фоновых воркеров на Windows, macOS и Linux.

## Шаг 0. Что нужно установить

1. **Docker Desktop** — https://www.docker.com/products/docker-desktop/
   (на Linux — Docker Engine + Compose plugin).
2. **Git** — https://git-scm.com/downloads.

3. **Python 3.12+** — для установки нормативных данных на хост.
4. **GitHub CLI** — https://cli.github.com/; учётная запись должна иметь доступ
   к приватному репозиторию.

Node и PostgreSQL живут внутри контейнеров.

Проверьте, что Docker работает:

```powershell
docker --version
docker compose version
```

Обе команды должны напечатать версии без ошибок. Если Docker Desktop только
что установлен — запустите его и дождитесь статуса «Running».

## Шаг 1. Скачать проект

```powershell
git clone https://github.com/KDFP-IT/smeta-checker.git
cd smeta-checker
git checkout dev
```

Затем войдите в GitHub CLI и установите нормативные данные:

```powershell
gh auth login
python scripts/install-normative-data.py
```

На macOS/Linux используйте `python3`. Скрипт скачивает архивы отдельно от Git,
проверяет SHA-256 и не перезаписывает существующие каталоги `base/` и
`normative-handoff-20261030-092929/`. Без этих каталогов стандартный Compose
не сможет смонтировать нормативные данные.

## Шаг 2. Создать файл с секретами

```powershell
Copy-Item .env.example .env   # Windows PowerShell
# cp .env.example .env        # macOS / Linux
```

Откройте `.env` в блокноте и заполните **минимум четыре значения**
(режим по умолчанию `WORKSPACE_AUTH_MODE=local`, пустое значение — тоже local):

| Переменная | Что вписать |
|---|---|
| `POSTGRES_PASSWORD` | Любой длинный пароль, например `smeta-2026-secret-pw` |
| `AUDIT_API_TOKEN` | Любой длинный случайный токен, например `smeta-api-token-2026-xyz` |
| `WORKSPACE_LOGIN` | Произвольный логин для входа (значение на ваш выбор) |
| `WORKSPACE_PASSWORD` | Произвольный длинный пароль для входа (значение на ваш выбор) |

Без `POSTGRES_PASSWORD`/`AUDIT_API_TOKEN` запуск остановится с понятной
ошибкой — это защита, а не баг. Без `WORKSPACE_LOGIN`/`WORKSPACE_PASSWORD`
в режиме local вход отвечает 503 и анонимного доступа нет: сначала экран
входа с логином и паролем. В `.env.example` оба значения оставлены пустыми
с пояснениями; реальные значения храните только в игнорируемом `.env`.

Для аудита дополнительно настройте одного провайдера модели: Yandex Cloud
(`YANDEX_CLOUD_API_KEY`, `YANDEX_CLOUD_FOLDER`), AnyModel (`ANYMODEL_API_KEY`,
`ANYMODEL_MODEL`) или RouterAI (`ROUTERAI_API_KEY`, `ROUTERAI_MODEL`). Без
настроенной модели запуск аудита недоступен. Фрагменты документов передаются
выбранному провайдеру, поэтому заранее проверьте условия обработки данных.

По умолчанию порт интерфейса привязан к `127.0.0.1`, но порт API
(`API_PORT`, по умолчанию 8000) Compose публикует на всех интерфейсах хоста.
До запуска ограничьте доступ к нему сетевым экраном: не выставляйте API в
интернет. Токен API не заменяет сетевую защиту.

## Шаг 3. Запустить сервисы

```powershell
docker compose up -d --build
```

При первом запуске Docker скачивает базовые образы и собирает образы приложения.

Проверьте статус:

```powershell
docker compose ps
```

Все сервисы должны быть `running` (у `migrate` — `exited (0)`, это нормально:
он один раз применил миграции и завершился).

## Шаг 4. Открыть в браузере

| Что | Адрес |
|---|---|
| **Nuxt-интерфейс (основной)** | http://127.0.0.1:3000 |
| API health | http://localhost:8000/healthz → `{"status":"ok"}` |

Откройте Nuxt — сначала экран входа: введите `WORKSPACE_LOGIN` и
`WORKSPACE_PASSWORD` из `.env`. Неверный или пустой логин/пароль отвечает
общим 401 без подсказки, что именно не совпало. Затем загрузите ВОР
(XLSX/CSV) и PDF, нажмите «Проверить», откройте позицию и скачайте Word-отчёт.

## Шаг 5 (необязательно). Проверить доступность API

```sh
docker compose exec -T api curl -fsS http://127.0.0.1:8000/healthz
```

Ответ `{"status":"ok"}` подтверждает доступность API внутри контейнера, но не
проверяет вход, работу модели или качество аудита. Сценарии разработки и
тестирования описаны в [руководстве разработчика](development.md).

## Вход: два режима без анонимного доступа

`WORKSPACE_AUTH_MODE` принимает ровно два значения: `local` (по умолчанию,
пустое значение — тоже `local`) и `ldap`. Анонимного режима нет: переход
к защищённой странице возвращает на форму входа, API и файлы проверяют сессию на сервере.

Режим local — пара `WORKSPACE_LOGIN` + `WORKSPACE_PASSWORD` из `.env`
(оба обязательны):

```env
WORKSPACE_AUTH_MODE=local
WORKSPACE_LOGIN=произвольный-логин
WORKSPACE_PASSWORD=произвольный-длинный-пароль
```

Логин чувствителен к регистру (пробелы по краям отбрасываются), пароль
сравнивается точно, без обрезки пробелов. Неверный или пустой логин/пароль —
общий 401. Отсутствующие `WORKSPACE_LOGIN`/`WORKSPACE_PASSWORD` — 503 входа,
сессия не выдаётся. Опечатка в `WORKSPACE_AUTH_MODE` — 503. В режиме local
LDAP-вызовы не выполняются, параметры `LDAP_*` игнорируются. Учётная запись
сессии — настроенный `WORKSPACE_LOGIN`; старые сессии псевдо-аккаунта
не принимаются. Лимиты входа те же, что для AD: 3 попытки на учётную запись
и 20 с IP за 15 минут, включая успешные попытки.

Режим ldap — корпоративный вход Active Directory (режимов входа по-прежнему
ровно два: local|ldap; `LDAP_ACCESS_MODE` и `LDAP_TLS_MODE` третьего режима
не добавляют). Политика авторизации — `LDAP_ACCESS_MODE` (пусто = `group`,
безопасное значение по умолчанию): `group` требует полный `LDAP_GROUP_DN`
и пускает только членов этой группы с учётом вложенных групп AD; `all` пускает
любую активную/разблокированную/неистёкшую учётную запись-пользователя
в `LDAP_BASE_DN`, кроме служебной записи поиска (роли сотрудников не выводятся,
прочие служебные записи с верным паролем тоже проходят). Пустой
`LDAP_GROUP_DN` — не «все»: в `group` он обязателен, в `all` игнорируется
(оставьте пустым). Для `all` нужен полный DN в `LDAP_BIND_DN`, не UPN/короткое
имя; в `group` допустимы полный DN и UPN.

```env
WORKSPACE_AUTH_MODE=ldap
WORKSPACE_ORIGIN=https://smeta.kdfp.ru
LDAP_URL=ldaps://подтверждённый-сервер:порт
LDAP_TLS_MODE=
LDAP_BASE_DN=подтверждённый-DN
LDAP_DOMAIN=подтверждённый-домен
LDAP_BIND_DN=подтверждённая-служебная-запись
LDAP_BIND_PASSWORD=
LDAP_ACCESS_MODE=
LDAP_GROUP_DN=подтверждённый-DN-группы-только-для-group
```

Пустой `LDAP_TLS_MODE` = безопасно по умолчанию: `ldaps://` → LDAPS,
`ldap://` → обязательный STARTTLS до обоих bind. Явные значения
`ldaps|starttls|none`; `none` — только для `ldap://`, `starttls` — только для
`ldap://`, `ldaps` — только для `ldaps://`. Несовпадение схемы/режима
и неизвестное значение запрещают вход до открытия сокетов. Ошибка TLS
в безопасных режимах никогда не откатывается в `none`; проверка цепочки
и имени сервера не отключается.

Подтверждённый пример внутренней сети — явный opt-in пользователя
(как Bitrix, по умолчанию остаётся безопасный режим):

```env
WORKSPACE_AUTH_MODE=ldap
LDAP_URL=ldap://192.168.30.200:389
LDAP_TLS_MODE=none
LDAP_BASE_DN=DC=kdfp,DC=ru
LDAP_DOMAIN=kdfp.ru
LDAP_BIND_DN=CN=smeta,CN=Users,DC=kdfp,DC=ru
LDAP_BIND_PASSWORD=
LDAP_ACCESS_MODE=all
LDAP_GROUP_DN=
```

Живой разовый bind служебной записи успешен (ровно один результат поиска);
подтверждены DN `CN=smeta,CN=Users,DC=kdfp,DC=ru` и UPN `smeta@kdfp.ru`.
Запись `smeta` — только поиск, прав администратора не требует. Вход сотрудника
сквозной проверкой до конца не проходил: для `all` нужна реальная учётная
запись сотрудника, для `group` — дополнительно groupDN, его получите
у администратора AD. Пароли в пример не вписывайте, храните только
в игнорируемом `.env`.
Риск `none`: служебный пароль и вводимый пароль сотрудника идут
незашифрованными на участке ПК/сервер → AD; Tailscale/HTTPS сайта этот
LAN-участок не шифруют. `none` не отключает HTTPS сайта и Secure-cookie
и не добавляет третий режим входа.

LDAP-значения вне подтверждённого примера не угадывать: получите их
у администратора AD (подробности ниже).
Недоступность AD в режиме ldap отвечает 503 и никогда не откатывается на local.
Скрипт `scripts/verify-ad.mjs` проверяет только режим ldap.

## Доступ из локальной сети (интранет)

По умолчанию Nuxt слушает только localhost сервера. Чтобы открыть его
с других машин компании:

1. В `.env` укажите адрес сервера, откройте порт наружу и задайте локальную
   пару входа (режим по умолчанию `local`):

```env
NUXT_PUBLIC_HOST=192.168.1.10
WORKSPACE_BIND=0.0.0.0
WORKSPACE_AUTH_MODE=local
WORKSPACE_LOGIN=произвольный-логин
WORKSPACE_PASSWORD=произвольный-длинный-пароль
```

2. Перезапустите: `docker compose up -d`.
3. Откройте `http://192.168.1.10:3000` с любой машины сети — сначала экран
   входа с логином и паролем.

BFF принимает только точный Host — подмена адреса даст 403. Вход по
логину+паролю обязателен и в этом режиме: анонимного доступа нет. Защита
Host/CSRF сохраняется, базы пользователей/ролей и регистрации нет — это одно
общее рабочее пространство.

## Доступ из интернета (мировая сеть)

1. В `.env` укажите домен и локальные логин+пароль. Оставьте интерфейс
   привязанным к localhost, чтобы его нельзя было открыть в обход TLS-прокси:

```env
NUXT_PUBLIC_HOST=audit.example.com
WORKSPACE_AUTH_MODE=local
WORKSPACE_LOGIN=произвольный-логин
WORKSPACE_PASSWORD=произвольный-длинный-пароль
WORKSPACE_BIND=127.0.0.1
```

2. Перед контейнером поставьте reverse proxy с TLS (nginx/Caddy/Traefik),
   терминирующий HTTPS и проксирующий на `127.0.0.1:3000`.
3. Перезапустите: `docker compose up -d`.
4. Откройте `https://audit.example.com` — сначала экран входа с логином и паролем.

Без TLS логин, пароль и документы летят открытым текстом — так разворачивать
запрещено. Сессия живёт не более 8 часов, cookie HttpOnly + SameSite=Strict.

## Корпоративный вход Active Directory

**По умолчанию выключен (`WORKSPACE_AUTH_MODE` пуст = local). На `smeta.kdfp.ru`
не включать без отдельной команды.** Подтверждены: IP AD `192.168.30.200`,
DNS-имя `kdfp-dc1.kdfp.ru`, домен `kdfp.ru`, `defaultNamingContext DC=kdfp,DC=ru`;
оба TCP-порта доступны с Windows-ПК (`n.gritsenko@100.126.198.65` по SSH).
Живой разовый bind записи `smeta` успешен (ровно один результат поиска);
подтверждены DN `CN=smeta,CN=Users,DC=kdfp,DC=ru` и UPN `smeta@kdfp.ru`.
Вход сотрудника с паролем и положительная групповая авторизация не проверены.
Политика `all` проверена на реальном AD из Docker: активная запись получает
разрешение без группы, служебная запись отклоняется, включая алиасы логина
и эквивалентные написания DN. Проверка доступа не заменяет вход с паролем.
Наблюдалось ранее: живой STARTTLS — ошибка инициализации SSL/TLS 52, LDAPS —
сброс соединения. Сертификат HTTPS сайта не заменяет сертификат AD.

### Что получить у системного администратора

| Настройка | Требуемые данные |
|---|---|
| `LDAP_URL` | Имя контроллера, совпадающее с SAN сертификата, явный протокол и порт. `ldaps://…:…` либо `ldap://…:…`; по умолчанию `ldaps://` → LDAPS, `ldap://` → обязательный STARTTLS. Явный `LDAP_TLS_MODE=none` — только для `ldap://` как opt-in внутренней сети (как Bitrix) |
| `LDAP_TLS_MODE` | Пусто = безопасно по умолчанию (см. выше). Явные `ldaps\|starttls\|none`; `none` только для `ldap://`, `starttls` только для `ldap://`, `ldaps` только для `ldaps://` |
| `LDAP_BASE_DN` | Полный DN области поиска сотрудников (подтверждён `DC=kdfp,DC=ru`) |
| `LDAP_DOMAIN` | Домен корпоративного логина (подтверждён `kdfp.ru`); подтвердить формат логина |
| `LDAP_BIND_DN`, `LDAP_BIND_PASSWORD` | Служебная запись `smeta`, только поиск пользователей/групп: DN `CN=smeta,CN=Users,DC=kdfp,DC=ru`, UPN `smeta@kdfp.ru` (живой bind успешен); прав администратора не требует. Для `LDAP_ACCESS_MODE=all` нужен полный DN, не UPN/короткое имя |
| `LDAP_ACCESS_MODE` | Политика авторизации: пусто = `group` (по умолчанию, безопасно). `group` требует `LDAP_GROUP_DN` и пускает только членов группы с вложенными; `all` пускает любую активную/разблокированную/неистёкшую учётную запись-пользователя в `LDAP_BASE_DN`, кроме служебной записи |
| `LDAP_GROUP_DN` | Полный DN разрешённой группы — только для `group` (до сих пор не подтверждён, получите у администратора; сервер проверяет и вложенные группы через AD matching rule in chain). В `all` игнорируется, оставьте пустым; пустое значение — не «все» |
| Политика блокировки AD | Порог и окно блокировки; согласовать локальный лимит **3 попытки/учётную запись и 20/IP за 15 минут**, включая успешные входы |
| Тестовые записи | Для `all`: активный сотрудник в `LDAP_BASE_DN`; для `group`: разрешённый сотрудник, сотрудник вне группы, сотрудник через вложенную группу; согласовать отрицательные проверки без блокировки рабочих записей |
| Сеть | DNS и маршрут из Docker до AD, firewall, доступность Redis |

Вне подтверждённого выше примера (`192.168.30.200`, `DC=kdfp,DC=ru`, `kdfp.ru`)
не подставляйте предполагаемые bindDN, groupDN, порт или TLS-режим.
Если NetBIOS-имя и UPN-суффикс различаются, используйте согласованный
с `LDAP_DOMAIN` формат, не добавляйте неподтверждённые алиасы.

### Настройка согласованного стенда

Секреты — только в игнорируемом `.env` или окружении. В `.env.example`
LDAP-значения оставлены пустыми. Заполните подтверждённые параметры выше,
задайте `WORKSPACE_AUTH_MODE=ldap` и `WORKSPACE_ORIGIN=https://smeta.kdfp.ru`
(на тестовом стенде — его точный HTTPS origin).
Compose передаёт `WORKSPACE_REDIS_URL=redis://redis:6379/1`; Redis недоступен —
новые входы и запросы с сессией запрещены. Python API-токен не меняется.

Для внутреннего CA задайте **абсолютный** `LDAP_CA_HOST_FILE` на Docker-хосте:

```sh
docker compose -f compose.yaml -f compose.ldap-ca.yaml config --quiet
# Только на согласованном стенде, не команда переключения production:
docker compose -f compose.yaml -f compose.ldap-ca.yaml up -d --build workspace
```

Дополнение монтирует существующий PEM-файл read-only в `/run/certs/ad-ca.pem`
и задаёт `LDAP_CA_FILE` внутри контейнера; отсутствующий файл не создаётся
как каталог. Если CA публичный, дополнение не требуется, `LDAP_CA_FILE` пуст.
Не копируйте CA/ключи в образ или репозиторий.

По умолчанию TLS не ниже 1.2, проверяются цепочка и имя сервера,
проверка не отключается. Для `ldap://` при пустом `LDAP_TLS_MODE` STARTTLS
выполняется **до обоих bind и перед перепроверками**; ошибка TLS запрещает
вход, без plaintext fallback. Явный `LDAP_TLS_MODE=none` (только `ldap://`,
только сознательный opt-in) пропускает TLS перед обоими bind и перепроверками;
служебный и вводимый пароли идут незашифрованными на участке ПК/сервер → AD.
Несовпадение схемы/режима и неизвестное значение запрещают вход до сокетов.
Логин ищется служебной записью, требуется ровно один результат; пароль
проверяется отдельным bind пользователя. Пароль не записывается в Redis,
cookie, браузерное хранилище, логи или Langfuse.

### Reverse proxy и ограничения доступа

Прокси должен завершать HTTPS, передавать исходный `Host` (включая нестандартный
порт, если он есть) и `Origin` без изменений. Порт workspace оставьте на
`127.0.0.1`, Python API и Redis не выставляйте в интернет.
Ни один режим не использует `X-Forwarded-For/Host/Proto` и не разрешает их
подменой менять адрес клиента или CSRF origin. За общим прокси IP-лимит
**20/15 минут общий для всех входов**; до запуска согласуйте дополнительный
лимитер на edge с администратором. `NUXT_TRUST_PROXY=1` относится только
к loopback-публикации порта Docker, не даёт доверия forwarded-заголовкам.

Cookie `kdfp_workspace`: новый случайный ID, HttpOnly + Secure + SameSite=Strict.
Серверная сессия имеет абсолютный срок 8 часов. Каждые 5 минут при очередном
запросе перепроверяются доступ/статус AD в рамках выбранной политики
(`group` — членство в `LDAP_GROUP_DN`, `all` — статус/существование записи
в `LDAP_BASE_DN` без служебной записи); отключение в AD не прерывает уже
выполняющийся запрос или поток скачивания. До перепроверки доступ может

### Принудительный отзыв

Compose использует отдельную Redis DB 1 для доступа (Celery — DB 0).
Следующие команды не удаляют документы и не очищают Redis:

```sh
# Все текущие сессии:
docker compose exec redis redis-cli -n 1 INCR kdfp:agen
# Один сотрудник: нижний регистр нормализованного account, без доменного префикса.
# Для спецсимволов используйте encodeURIComponent(account).
docker compose exec redis redis-cli -n 1 INCR kdfp:ugen:ivanov
```

Изменяется поколение: следующий запрос со старой сессией получает 401,
записи удаляются по TTL. Новые входы после отзыва разрешены, если доступ AD
сохранён; чтобы запретить их, отключите запись/доступ в AD.
Не применяйте `FLUSHDB/FLUSHALL`: это затронет другие данные.

### Реальная приёмка из Docker

После согласования стенда передайте в окружение **контейнера** временные
`WORKSPACE_TEST_URL` (точный HTTPS origin), `LDAP_TEST_LOGIN`,
`LDAP_TEST_PASSWORD`; не пишите пароль в командную строку/history,
отчёт или коммит. Для защищённой передачи используйте механизм секретов
вашего окружения/временный игнорируемый env-файл с правами 0600.
Скрипт поставляется в runtime-образе:

```sh
docker compose exec -T -e WORKSPACE_TEST_URL -e LDAP_TEST_LOGIN -e LDAP_TEST_PASSWORD workspace node scripts/verify-ad.mjs
```

Проверяется реальный путь HTTPS → Nuxt → AD: вход, cookie-флаги, сессия,
страница, защищённый API, выход, повтор старой cookie и запрет скачивания.
Скрипт не вызывает LLM и не меняет документы. После проверки уберите
тестовые переменные. Для `group` отдельно проверьте аккаунты вне группы/через
вложенную группу, для `all` — недоступность служебной записи и отзыв команды
выше. Unit-проверки используют тестовые LDAP-клиенты и не заменяют эту приёмку.

**Фактический вход сотрудника не заявляется: нет тестового пароля сотрудника.
На реальном AD из Docker подтверждены служебный bind, авторизация активной
записи в `all` и отказ служебной записи. В собранном Nuxt-контейнере без группы
проверены отказы API/скачиваний без сессии и отказ входа служебной записи.
Полный HTTPS-сценарий вход → защищённая страница → выход ещё не проверен.
Живые STARTTLS (ошибка 52) и LDAPS (сброс) ранее неуспешны; положительная
групповая авторизация не подтверждена. Production не изменялся.**

### Диагностика без секретов

- 401: общее сообщение для неизвестного логина, неверного пароля, отсутствия
  доступа по выбранной политике (`group` — вне группы, `all` — неактивная/
  заблокированная/истёкшая запись либо служебная запись) и исчерпания лимита.
  Не повторяйте неверный bind автоматически.
- 503 входа и инфраструктуры: отсутствует `WORKSPACE_LOGIN`/`WORKSPACE_PASSWORD`
  (local), опечатка в `WORKSPACE_AUTH_MODE`, неизвестное `LDAP_ACCESS_MODE`,
  незаполненные/недоступные параметры AD (ldap: в `group` — пустой
  `LDAP_GROUP_DN`; в `all` — не полный DN в `LDAP_BIND_DN`), несовпадение
  `LDAP_URL`/`LDAP_TLS_MODE` или неизвестный `LDAP_TLS_MODE`. Недоступность AD
  никогда не откатывается на local и никогда не откатывается в `none`.
  Проверьте также DNS-имя
  `kdfp-dc1.kdfp.ru`/IP `192.168.30.200`, маршрут/порт из контейнера, Redis,
  срок/SAN/цепочку сертификата AD и чтение CA пользователем `node`.
- 403: проверьте raw Host и точный HTTPS Origin; альтернативный порт/схема
  отклоняются, forwarded-заголовки не исправляют несовпадение.
- Не включайте TLS bypass (`NODE_TLS_REJECT_UNAUTHORIZED=0`), логирование
  тела `/api/session`, LDAP debug или запись тела входа на reverse proxy/APM.
- Обновляйте CA и служебный пароль через окружение/read-only mount;
  после изменения пересоздайте workspace на согласованном стенде.

## Частые действия

```powershell
docker compose logs -f api          # смотреть лог API (Ctrl+C — выйти)
docker compose logs -f workspace    # смотреть лог Nuxt
docker compose restart worker-llm   # мягкий рестарт воркера
docker compose down                 # остановить всё (данные сохранятся)
docker compose up -d                # запустить снова
```

| Симптом | Что делать |
|---|---|
| `Set POSTGRES_PASSWORD in .env` | Вы пропустили шаг 2: заполните `.env` |
| Порт занят (`port is already allocated`) | Закройте программу на порту 3000/8000, либо задайте `WORKSPACE_PORT`/`API_PORT` в `.env` |
| `workspace` отвечает 403 | Открывайте через адрес из `NUXT_PUBLIC_HOST` (или `http://127.0.0.1:3000`, если хост не задан). Подмена Host запрещена |
| Экран входа отвечает 503 | Проверьте `WORKSPACE_AUTH_MODE` (ровно `local` или `ldap`), `WORKSPACE_LOGIN`/`WORKSPACE_PASSWORD` в local и параметры AD в ldap (`LDAP_ACCESS_MODE` — ровно `group` или `all`, в `group` — заполненный `LDAP_GROUP_DN`, в `all` — полный DN в `LDAP_BIND_DN`) |
| Контейнер `unhealthy` дольше 2 минут | `docker compose logs <имя>` — там причина; чаще всего не дождались первой сборки |
| Всё сломалось и хотите с нуля | `docker compose down -v` (**сотрёт данные БД!**), затем шаг 3 |

## Как это устроено (кратко)

```text
Браузер → workspace (Nuxt, :3000) → api (FastAPI, :8000) → db (PostgreSQL)
                                                          → redis → worker-pdf / worker-llm
```

Данные живут в Docker volumes (`pgdata`, `blobs`, `pdfcache`, `redisdata`)
и переживают перезапуск. Бэкап: `./backend/scripts/backup.sh`.
