# Резервное копирование, перенос и миграции

Рабочие проекты, редакции и результаты хранятся в PostgreSQL, файлы ВОР/ПД и отчёты — в blob-хранилище. Снимайте и переносите **оба**: один дамп БД не восстанавливает файлы. Копия содержит документы и результаты: ограничьте доступ, храните её отдельно от сервера и не добавляйте в Git. Секреты `.env` в копию не входят; перенесите их отдельно защищённым способом или настройте заново.

## Создание копии

`backend/scripts/backup.sh` выполняет `pg_dump` работающей БД и затем копирует blobs из контейнера API; эти операции не атомарны. Для согласованной копии остановите приём запросов и дождитесь окончания проверок, затем остановите обработчики и relay. API для копирования blobs и БД должны оставаться запущенными. Запускайте команды из корня проекта:

```bash
docker compose stop workspace worker-pdf worker-llm worker-normative task-relay
# Если POSTGRES_USER или POSTGRES_DB отличаются от smeta, экспортируйте их
# в окружение shell: backup.sh не загружает их из .env самостоятельно.
make backup
```

Создаётся `backups/<UTC-stamp>/` с `db.dump`, `blobs/` и `manifest.txt`. При использовании нестандартного Compose-проекта или `compose.local.yaml` эти скрипты не учитывают дополнительные `-p`, `--env-file` и `-f`: не применяйте их к такому стенду без адаптации команд. Сохраните также версию исходников и конфигурацию развёртывания; manifest не содержит commit или версию схемы. После копирования запустите полный стек `docker compose up -d`.

## Восстановление на другом стенде

Восстановление **удаляет существующую целевую БД и заменяет её дампом, а также очищает каталог blobs**. Выберите изолированный целевой стенд; перед восстановлением имеющего данные стенда сделайте его отдельную копию. Используйте ту же версию исходников и схемы, что и при создании копии: скрипт запускает сервисы сразу после восстановления и до последующего обновления миграций. Установите нормативные данные и заполните `.env`, как описано в [быстром запуске](docker-quickstart.md). Скопируйте каталог копии целиком. Для нестандартных `POSTGRES_USER`/`POSTGRES_DB` задайте те же значения в `.env` целевого стенда.

```bash
# Создайте необходимые образы и контейнеры, затем исключите обработку задач.
docker compose up -d --build
docker compose stop workspace worker-pdf worker-llm worker-normative task-relay
make restore SRC=backups/20261102T120000Z  # замените на имя каталога своей копии
```

Скрипт проверяет `db.dump` и `manifest.txt`, останавливает API, workspace и два основных воркера, пересоздаёт БД через `pg_restore`, копирует blobs и запускает остановленные сервисы. **Он не останавливает `worker-normative` и `task-relay`** — их необходимо остановить заранее. Он также не переносит и не очищает Redis: используйте отдельный чистый Redis целевого стенда, чтобы старые очереди и сессии не смешались с восстановленными данными. После успешного восстановления поднимите остальные сервисы и актуальные миграции полным комплектом:

```bash
docker compose up -d --build
```

Проверьте на целевом стенде открытие проектов, исходных файлов и отчётов. Копия не включает `.env`, нормативные корпуса, Redis и `pdfcache`; для нормативного этапа нужна совместимая версия корпусов. Сценарий копирования не делает проверку целостности всей пары БД/blobs. Возобновление старых незавершённых проверок описано в [resumable-audits.md](resumable-audits.md).

`make dev` — отдельный вспомогательный сценарий: при пустой БД он может автоматически восстановить последнюю копию из `backups/`. `backend/scripts/dev.sh <путь>` принудительно восстанавливает копию, а `--fresh` удаляет перечисленные в скрипте volumes. Эти операции не используйте как обычный запуск или на рабочем сервере.

## Обновление схемы

Перед обновлением сохраните согласованную копию. В Compose одноразовый сервис `migrate` выполняет `alembic upgrade head` до запуска зависимых сервисов. Обновляйте API, workspace, воркеры и relay одним комплектом: `docker compose up -d --build`. Список последовательных миграций находится в `backend/alembic/versions/`.

Историческая миграция `0003_document_lifecycle` сохраняет UUID документов, версий и запусков, переносит имена в редакции и восстанавливает связи снимков ПД; старые документы не объединяются. Для старых данных действующей становится последняя редакция ВОР и первая редакция ПД. Откат к схеме с уникальностью имени может потребовать разрешения конфликтов одноимённых документов: это не замена восстановлению из копии.
