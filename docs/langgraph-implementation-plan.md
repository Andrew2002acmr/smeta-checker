# План перехода ядра проверки ВОР ↔ ПД на LangGraph

Статус: проект реализации, не выполненная миграция. Дата: 2026-10-22.

## 1. Решение и границы

Перестроить проверку одной позиции на управляемый LangGraph workflow с одним ограниченным агентом поиска. Не переписывать приложение и не создавать команду свободно общающихся «экспертов».

Сохранить Nuxt, HTTP/BFF, PostgreSQL, blob-хранилище, Celery, PDF/OCR, загрузку XLSX, Word и Phoenix. Сохранить рабочие функции разбора величин и проверки формул, но проверить их доменную применимость. LangGraph отвечает за переходы между этапами, а не за истинность заключения.

Код определяет итоговый статус по проверенным доказательствам. Модель предлагает поисковые действия и связи между фрагментами, но не утверждает сама себе достоверность источника и не назначает окончательную очередь.

Не устанавливать LangChain целиком ради графа. Базовое решение — `langgraph` и совместимый PostgreSQL checkpointer; существующий OpenAI-клиент можно вызывать из узлов. Дополнительный provider adapter добавлять только если доказана необходимость.

### Что не входит в миграцию

- Новый дизайн, новая система авторизации, смена модели или OCR-движка.
- Перенос воркеров в LangGraph Server, LangSmith или облачную платформу.
- Автоматическая замена библиотеки поиска на vector DB/embeddings без сравнения качества.
- Автоматическое исправление исходного ВОР.
- Изменение исторических отчётов и результатов.
- Изменение `PositionSource`, карты `cells` и публичных DTO без отдельного решения.

Текущий запрет новых живых прогонов после сработавшего стоп-критерия сохраняется. Этот документ не запускает миграцию, не возобновляет прогоны и не меняет действующие критерии приёмки.

## 3. Неподвижные инварианты

1. Источник — конкретная версия PDF, physical page, таблица/ячейка либо текстовый блок. Номер печатной страницы хранить отдельно, если он установлен.
2. Цитата дословная относительно доступного источника. Нормализованный текст нужен для поиска, но не подменяет цитату.
3. Совпадение числа, темы или слова не доказывает принадлежность величины нужной работе.
4. Native не означает автоматически `usable`; OCR не означает автоматически недостоверность. Учитывать качество конкретной структуры и привязки.
5. `uncertain` не превращается в подтверждение из-за уверенности модели или наличия HTML.
6. Не найдено — не отсутствие работы в документе. Отсутствие в проверенной области и исчерпание бюджета показывать раздельно.
7. Противоречие требует применимого доказательства; сомнительный OCR сам по себе не делает строку красной.
8. Несколько агентов или повторов с одинаковым ответом не являются независимыми доказательствами.
9. Повторные вызовы и возобновление графа не обнуляют бюджет позиции.
10. Не выводить разницу между несовместимыми величинами: расстояние 100 м нельзя вычитать из 45 точек.
11. Итоговый текст, числа, ссылки, очередь и Word должны выводиться из одного набора проверок.
12. В production не должно остаться двух конкурирующих аудиторов и silent fallback на старый алгоритм.

## 4. Данные: требования, доказательства, проверки

### 4.1. Требование `Requirement`

Внутренняя типизированная модель, не изменение frozen DTO:

- `requirement_id`, `kind`: наличие, количество, единица, метод, техническое условие, основание.
- `expected`: исходное значение и нормализованная величина, если её можно однозначно получить.
- `subject`: работа/материал, участок/раздел, документная связь.
- `source`: книга, лист, адрес ячейки, исходный текст, формула/зависимости.
- `required`: влияет ли требование на итог; причина обязательности.
- `derivation`: правило и его версия, а для LLM-декомпозиции — исходный текстовый диапазон.

Сначала извлекать явные поля из Excel кодом. Модель допускается для декомпозиции сложного названия/примечания, но каждое предложенное требование обязано ссылаться на фрагмент ВОР. Нельзя превращать информационную ссылку на норматив в самостоятельное обязательное доказательство наличия работы.

### 4.2. Доказательство `EvidenceRecord`

- Стабильный `evidence_id` от версии документа, страницы и source locator.
- `document_version_id`, `pdf_sha256`, `physical_page`; `printed_page` отдельно и только при установленном соответствии.
- `source_id`, `table_id`, `cell_ids`, `header_ids`, bbox и origin, если доступны.
- Точная цитата, нормализованный поисковый текст отдельно.
- Качество извлечения, структуры таблицы и привязки: это разные признаки.
- Предлагаемая связь с требованиями и субъектом работы.
- Результат проверки этой связи и причины принятия/отклонения.

Отклонённые источники не исчезают: сохранять причины для диагностики, но не включать их в подтверждённые величины.

### 4.3. Величина `MeasurementFact`

Нельзя хранить `9/45` как безымянное число либо выбирать ту часть, которая совпала с ВОР.

Для пары хранить два операнда:

- значение `9`, единица/роль `точка`;
- значение `45`, единица/роль `измерение`;
- порядок частей из заголовка `точка / измерение`;
- привязка к одной строке таблицы;
- идентификаторы источников числа, единицы, субъекта и связи.

Аналогично различать `receiver_spacing`, `source_spacing`, `electrode_spacing`, `survey_point_count`, `setup_count`, `measurement_count`. Текст «наблюдение» не объявлять безусловным синонимом всех этих понятий.

Связь «камеральная обработка наследует полевой объём» должна храниться отдельным проверяемым отношением: тот же метод, объект/участок и применимая единица тарифа. Это не глобальное правило совпадения названия. Если нормативная эквивалентность не установлена, отношение остаётся на ручную проверку.

### 4.4. Проверка `RequirementCheck`

Использовать существующий смысл состояний: `confirmed`, `contradiction`, `not_found`, `source_conflict`, `review_required`, `not_applicable`.

Каждая проверка содержит evidence IDs, ожидаемую/фактическую величину, machine-readable reason, границы поиска и незакрытый вопрос. Ошибки провайдера, подготовки и OCR хранятся отдельно от доменных противоречий.

### 4.5. Канонический результат `PositionAssessment`

Содержит все требования и проверки, применимые доказательства, составные величины, ограничения покрытия, ошибки выполнения и итог по существующим правилам приоритета.

Presentation строится только после оценки. Нельзя сохранять отрицательное объяснение первого раунда, если последующий раунд уже подтвердил требование. Модель не пишет окончательный вердикт независимо от `RequirementCheck`.

## 5. Состояние графа и runtime-зависимости

### Сериализуемый `AuditGraphState`

| Группа | Поля |
| --- | --- |
| Идентичность | run_id, position_index, document versions, corpus_id, graph_version, policy_version, prompt_version |
| Вход | snapshot reference, ссылка на ВОР-позицию и её неизменяемый хеш |
| Требования | requirements, classification и проверяемое основание классификации |
| Поиск | search actions, visited source IDs, query fingerprints, cursor/coverage, unresolved requirement IDs |
| Доказательства | evidence references и проверки привязки; большие байты отдельно в blob store |
| Величины | нормализованные атомарные и составные measurement facts |
| Исполнение | deadline, budget limits/usage/reservations, counters, error records, stop_reason |
| Выход | requirement checks, canonical assessment, terminal state |

`Decimal` сериализовать без потери точности, например строкой. Контрольные суммы строить по канонической сериализации. Порядок merge evidence задавать по IDs, а не по случайному порядку ответа.

### Runtime context, не checkpoint state

Клиент модели, секреты, соединения PostgreSQL, blob store, восстановленный индекс, логгер и Phoenix callback. Не сохранять в checkpoint Python-объекты PDF, SQLAlchemy Session, ключи или весь документ в каждом шаге.

Начальный граф последовательный внутри позиции. Параллелизм — между позициями через Celery. Параллельное выполнение графовых веток не включать до появления доказанной необходимости: иначе усложняются общий бюджет, порядок результатов и возобновление.

| Узел | Реализация | Переход |

| `build_assessment` | Итог из проверок, вопросы по незакрытым требованиям, причины статуса | Возврат результата воркеру |

### Ветки со специальными стандартами доказательства

- Полевая работа: наличие метода и объектной связи отдельно от объёма.
- Камеральная: полевая строка не подтверждает всё автоматически; проверить отношение и единицу.
- Отчёт/программа: существование документа отдельно от самостоятельной сметной оплаты. Содержание с ссылкой на приложение — навигация, а не безусловное доказательство полного документа и количества.
- Нормативная: явно показать, что объём не проверяется по ПД; проверять доступное основание в ВОР/формуле. Без доступного нормативного источника не подтверждать правильность расценки.
- Неизвестная: не угадывать роль; ручная проверка с причиной.

### Условие завершения

Не завершать поиск только потому, что работа упомянута. Завершать, когда обязательные требования разрешены, получено применимое противоречие с достаточными данными либо достигнут явный предел.

`no_progress` — повтор того же действия без новых применимых доказательств, новых проверок или уменьшения неопределённости. Число написанных моделью токенов прогрессом не является.

## 7. Инструменты агента поиска

Все инструменты read-only относительно пользовательских документов; каждый возвращает типизированные данные, а не произвольный пересказ.

| Инструмент | Вход | Выход и ограничения |
| --- | --- | --- |
| `search_document` | requirement ID, query, document version, scope, cursor, filters | Ограниченные кандидаты с компонентами score, provenance и качеством; без подбора по ожидаемому числу |
| `read_page` | document version + physical page | Текст/блоки из snapshot, available quality, ссылки на таблицы; не весь PDF |
| `read_table` | table ID, диапазон данных | Полные строки с исходной шапкой, rowspan/colspan, пустыми ячейками и координатами |
| `read_related_section` | проверенный anchor + section ID | Методика/приложение с явной связью; соседняя страница сама по себе связи не доказывает |
| `inspect_source_quality` | source ID | Раздельные причины непригодности извлечения, структуры и subject binding |

Поиск не ограничивать навсегда текущим page scorer. Через один corpus API сравнить existing lexical, BM25/exact/RRF; выбрать по измерению evidence recall при одинаковом бюджете. Название таблицы не может быть единственным критерием релевантности, как это произошло с сейсмической таблицей для УЭС.

Сохранять разные поисковые поля: работа/метод, scope, единица, примечание, нормативная ссылка. Не складывать длинный комментарий о надбавках в один равноправный запрос с названием работы.

### OCR и изображения

Не открывать PyMuPDF в slim LLM worker. Доступный OCR уже входит в подготовленный snapshot. Если нужен новый OCR/рендер, его выполняет PDF worker по отдельной bounded задаче с новым immutable snapshot revision; граф продолжает работу только с явно принятой новой ревизией.

Изображение страницы можно использовать для проверки чтения/структуры только через реальный инструмент и провайдер с проверенной vision-поддержкой. Нельзя объявить vision-проверку по текстовому ответу модели. Если vision недоступен — явный пробел и ручная проверка, не фиктивный инструмент.

Новое асинхронное обогащение включать только после реализации хранения revisions, идемпотентного dispatch и resume. До этого агент честно возвращает `needs_ocr`; не делать неработающий tool-заглушку.

## 8. Бюджет и остановка

Бюджет реализовать кодом, а не системным промптом:

- общий deadline позиции;
- общее число реальных provider requests, включая repair и HTTP retries;
- input/output token limit и денежный предел при доступных тарифах;
- число поисковых действий, уникальных страниц, OCR-задач и итераций;
- предел размера каждого tool result;
- лимит no-progress;
- запрет повторного эквивалентного действия без новой причины.

Начальные численные значения выбрать после фиксации baseline. Не вписывать произвольный «магический» лимит как доказанно достаточный. При отсутствии достоверной цены действуют жёсткие token/request limits; денежная оценка помечается неизвестной.

Лимит LangGraph recursion — аварийный предохранитель, не замена бизнес-бюджету. Бюджетные остановки отображаются как ограничение проверки; 401/5xx не маскируются под отсутствие работы.

## 9. Persistence, Celery и повторное выполнение

### Разделение ответственности

- Celery: доставка задания, конкуренция воркеров, recovery умершего воркера.
- LangGraph: выполненные этапы и состояние проверки одной позиции.
- Repository: ownership задания, итоговый результат, статус и запуск общей финализации.

`thread_id`: детерминированный ключ из run_id, position_index и graph version. Resume того же задания использует тот же thread. Новый аудит — новый run и thread, а не перезапись прежнего состояния.

PostgreSQL checkpointer использовать в существующем PostgreSQL, без второго сервера БД. Setup таблиц выполнять в выделенном миграционном процессе, не при старте slim worker. Учесть различие существующего SQLAlchemy URL и DSN, который принимает checkpointer. Схему и необходимые права определить при внедрении.

### Дубликаты и crash windows

1. Перед invoke получить атомарное владение position job. Если текущего claim недостаточно для защиты от двух воркеров, добавить lease/fencing token внутренней миграцией.
2. Завершённое задание возвращает сохранённый результат без повторных LLM-вызовов.
3. Внутри графа разделить provider calls и операции записи на узлы с контролируемыми side effects.
4. Вести ledger внешних вызовов: request fingerprint, attempt, budget reservation, started/completed/unknown и response reference.
5. Упавший запрос с неизвестным исходом не считать бесплатным. Exactly-once billing не обещать: провайдер может принять запрос перед потерей соединения.
6. Итог фиксируется одной repository-транзакцией: result + terminal job state + защита от повторной финализации. Если граф завершён, но транзакция не прошла, recovery использует сохранённый terminal assessment.
7. Для dispatch финализации использовать существующий безопасный механизм либо transactional outbox, если тест crash window докажет его необходимость.
8. Бюджет и версия политики восстанавливаются из сохранённого состояния; restart не создаёт новую квоту.

Важное свойство LangGraph: checkpoint не означает сохранение в середине произвольной функции. При возобновлении незавершённый узел может выполниться заново. Платные вызовы и запись данных требуют явного проектирования идемпотентности.

### Рост хранилища и данные

Checkpoints содержат ссылки на большие артефакты, а не PDF/base64 каждого шага. Политика хранения: пока run активен — хранить необходимые checkpoints; после завершения — сохранять итог, обязательные доказательства и audit trail, промежуточные checkpoints удалять по согласованному retention. Не удалять blob, пока на него ссылается сохраняемый результат.

Пользовательские документы и цитаты считать чувствительными; маскирование Phoenix распространяется и на новые узлы. Секреты не попадают в state, prompts, логи, ledger и отчёты.

## 10. Результат, фронт и Word

Один `PositionAssessment` → один presenter → существующие публичные поля и Word.

Для №11:

- внутренний факт: 9 точек, 45 измерений;
- сравниваемая величина: 9 точек против 45 точек ВОР;
- дополнительное значение: 45 измерений;
- объяснение: обе величины и откуда взяты единицы;
- никаких «в проекте — .» и вычитания несовместимых ролей.

Сначала проверить, можно ли представить составную величину существующими строковыми полями без потери значения и без ложной численной дельты. Не менять типы публичных полей исподтишка. Если существующий DTO недостаточен — отдельный согласованный шаг изменения API с экспортом OpenAPI и генерацией SDK, а не обход frozen-контрактов.

Статус `ok` нельзя сочетать с собственным окончательным пояснением «объём не подтверждён», если его уже подтвердил принятый способ проверки. Для существования программы явно написать стандарт проверки существования, а не притворяться, что количество было напечатано в PDF.

В review показать подтверждённую часть и точный оставшийся вопрос. Для красной строки — применимое доказательство, страница и единицы. Навигационное расхождение номера страницы не превращать в расхождение объёма.

## 11. Наблюдаемость

Сохранить один Phoenix session на audit run и отдельные trace/span для позиции и узлов. В span записывать:

- requirement IDs, graph/policy/prompt versions;
- выбранное действие и причину;
- кандидатов и причины отбора/отклонения;
- принятые evidence IDs и качество;
- изменение состояния проверок;
- запросы, токены, время и бюджет;
- stop_reason, thread/checkpoint ID и номер resume.

Не дублировать один вызов в метриках из-за двух tracing integrations. Не вводить LangSmith параллельно Phoenix без необходимости. Ошибка телеметрии не должна менять доменный вердикт.

Диагностический вопрос, на который должны отвечать артефакты: «Почему требование объёма не подтверждено: нужная страница не извлечена, не найдена, не прочитана, не выбрана, источник отклонён или величина несопоставима?»

## 12. Порядок реализации и критерии завершения этапов

### Этап 0. Зафиксировать контракт и baseline

Действия:

1. Зафиксировать входы и последние результаты ИГФИ по хешам и run IDs; исторические результаты не править.
2. Выделить единый evaluation manifest: требования, допустимые альтернативные доказательства и типы расхождений. Не требовать одну точную формулировку модели.
3. Добавить контрольный набор из другого документа; его ожидаемые ответы должны быть проверены человеком до использования как gold. Отложить часть документов как holdout, не настраивать по ним поиск.
4. Зафиксировать версии модели и параметры генерации; одинаковые квоты при сравнении.
5. Согласовать противоречие критерия «каждая строка имеет PDF-страницу» и нормативных строк, где PDF не доказывает нормативную цену. До согласования не считать исходный критерий отменённым и не подставлять случайные страницы.
6. Согласовать, что partial остаётся queue `review`, а отличие от normative выражается проверками и текстом без новой очереди.

Выход: воспроизводимый baseline и manifest, перечень нерешённых договорённостей. Никакой уверенности модели вместо gold-разметки.

### Этап 1. Проверить зависимости и запуск минимального графа

Действия:

1. Выбрать и запинить совместимые `langgraph`/Postgres checkpointer под Python 3.14, текущий Pydantic и psycopg. Реальную совместимость проверить установкой и smoke; не полагаться на название версии.
2. Обновить `pyproject.toml`, `uv.lock` и воспроизводимо генерируемые dependency artifacts проекта; ручного редактирования lock нет.
3. Добавить внутренние state models и минимальный граф с реальными load/validate/terminal узлами, без fake auditor в production.
4. Добавить миграционную инициализацию checkpointer; проверить startup полного стека и импорт из slim worker.

Gate: граф сохраняет состояние в PostgreSQL и корректно возобновляется после остановки процесса; секретов в checkpoint нет. Это инфраструктурный gate, не готовая проверка документов.

### Этап 2. Разделить доменную модель и transport

Действия:

1. Выделить requirement/evidence/measurement/assessment contracts.
2. Выделить provider transport из `audit_llm.py`: allowlist хостов, текущие providers, token usage, обработка пустого ответа/обрыва и бюджет.
3. Перенести применимые функции сравнения из orchestration в независимый evaluator; не скопировать второй набор правил.
4. Нормализовать составные количества и роли геометрии/шагов/наблюдений.
5. Добавить предметные тесты для точек/измерений, несовместимых ролей, scope, частичных доказательств и отсутствующих значений.

Gate: один и тот же набор доказательств даёт одинаковые проверки без вызова модели; итог не зависит от свободного текста объяснения.

### Этап 3. Сделать corpus tools и управляемый поиск

Действия:

1. Вынести corpus API и сохранить snapshot provenance.
2. Реализовать search/read_page/read_table/read_related_section/quality tools с ограничениями размера.
3. Подключить имеющиеся поисковые каналы через один API; измерить recall на gold и holdout.
4. Добавить валидацию quote/source/row/header/scope и явные rejection reasons.
5. Реализовать планировщик одного поискового действия по незакрытому требованию, дедупликацию действий и no-progress.
6. Проверить изоляцию документа/проекта и prompt injection в тексте PDF: документ не является инструкцией агенту.

Gate: агент может добрать доказательство, не попавшее в первый контекст; не выдаёт другой документ или неподходящую таблицу за подтверждение.

### Этап 4. Собрать полный граф позиции

Действия:

1. Соединить узлы и условные переходы из раздела 6.
2. Реализовать разные политики для полевых, камеральных, документов и нормативных строк.
3. Пропустить граф через существующие независимые проверки ВОР без двойного переопределения статуса.
4. Включить ledger, budget, deadline, cancellation и ошибки выполнения.
5. Сформировать canonical assessment и presenter.

Gate: end-to-end smoke проходит от реальной позиции/snapshot до сериализованного результата и Word; структурированные тестовые ответы используются только в явном offline-тесте, не выдаются за live.

### Этап 5. Интегрировать долговечность и Celery

Действия:

1. Добавить graph invocation в `audit_tasks.audit_position`.
2. Реализовать ownership/fencing, terminal commit и recovery.
3. Проверить повторную доставку, потерю воркера до/после provider response, после terminal checkpoint и перед записью результата.
4. Проверить, что окончание всех позиций запускает ровно допустимую финализацию и не размножает Word.
5. При включении дополнительного PDF/OCR — реализовать реальную cross-queue задачу, snapshot revision и resume; иначе явно не рекламировать эту возможность.

Gate: перезапуск и повторная доставка не портят состояние, не обнуляют квоту и не подменяют документ. Возможность повторной оплаты незавершённого provider call явно отражена.

### Этап 6. Доказать качество и исправить presentation

Действия:

1. Сравнить baseline и graph engine отдельной evaluation-командой на одном corpus и одинаковом бюджете. Не включать двойной аудит в пользовательском production-запуске.
2. Выполнить несколько повторов с заранее установленным числом для оценки стабильности; не выбирать только удачный запуск.
3. Разобрать каждое изменение verdict и каждый ложный красный статус по evidence IDs.
4. Проверить экран строки, PDF-переход, исходные цитаты и скачанный Word.
5. Проверить desktop/узкий viewport, loading/error/empty и отсутствие raw source IDs в пользовательском заключении.

Gate: выполнены согласованные критерии раздела 13 и сохранён отчёт с артефактами. Если качество не выросло — не переключать production и не называть инфраструктурную миграцию исправлением аудита.

### Этап 7. Чистый cutover

Действия:

1. Новые запуски используют только граф.
2. Удалить старый production orchestration, временный evaluation selector, дублирующие prompts/retries/status writers и неиспользуемые зависимости.
3. Сохранить необходимые pure domain functions и чтение исторических сохранённых данных; это не fallback на старый аудитор.
4. Обновить README, Docker-инструкцию, описание лимитов и диагностики.
5. Повторить smoke после удаления старого пути, а не только до него.

Gate: один production entry point и один источник итогового вердикта. Откат — развёртывание прежнего артефакта, а не скрытый runtime fallback. Не откатывать разрушительно БД; старое приложение должно быть проверено на совместимость с additive миграциями, незавершённые новые runs остаются явно versioned.

## 13. Приёмка и оценка качества

### ИГФИ: наблюдаемые результаты

| Позиции | Критерий |
| --- | --- |
| 3 и 11 | Найдена строка 9/45 с заголовком единиц, числа не выбраны по совпадению с ВОР; в UI/Word видны 9 точек и 45 измерений |
| 1 | 8 точек, 2,5 м между приёмниками и 11,5 м между источниками не смешиваются; вопрос по волнам/наименованию явно отделён от количества |
| 2 | 3 точки и 6 измерений отделены от шага 1 км и базы электродов 100 м |
| 7 и 8 | Наличие общего отчёта не доказывает раздельную оплату; сформулирован вопрос раздельного учёта |
| 9 | Проверено существование программы по применимому документному доказательству, а не одному слову «программа» |
| 10 и 12 | Проверена связь с полевыми работами и единица учёта; нет безусловного переноса количества от похожей строки |
| 4, 5, 6, 13 | Явно нормативные строки; нет выдуманного PDF-подтверждения цены/коэффициента |

Целевые очереди исходной задачи остаются в manifest как пользовательские ожидания. Если проверяемые данные им противоречат, оформляется разбор с цитатой, а не правило по номеру позиции. Система должна обобщаться на другой ВОР.

### Измеряемые показатели

- Evidence recall: найдены ли необходимые доказательства в пределах бюджета.
- Evidence validity: цитата, документ, страница, шапка и привязка верны.
- Claim accuracy: количество/единица/метод/условие оценены отдельно.
- False-red count: число ложных доказанных расхождений.
- Coverage: что осталось непроверенным и по какой причине.
- Stability: результаты всех повторов, а не лучший прогон.
- Requests, tokens, стоимость с обозначением неизвестных тарифов, длительность и recovery overhead.

Gate запуска: ни одного ложного красного на согласованном acceptance corpus; ни одной выдуманной цитаты или перестановки ролей составного количества; непротиворечивые UI и Word; остальные количественные пороги зафиксировать по baseline до настройки. Не объявлять это доказательством нулевой ошибки на всех будущих документах.

### Постоянные регрессии

- Перестановка единиц пары, неполная шапка, 9/45 без надёжного соответствия единиц.
- Число нужного размера в чужой строке/разделе/документе.
- Противоречащие применимые источники против сомнительного OCR-дубля.
- Полное подтверждение и честная остановка с незакрытым требованием.
- Устаревший текст объяснения после успешного добора.
- Значения в UI/Word не пустые и не противоречат checks.
- Budget/deadline/no-progress после resume.
- Duplicate delivery, crash windows и cancellation.
- PDF prompt injection и попытка модели вызвать неразрешённый инструмент.

Не тестировать точную прозу модели, названия узлов и совпадение mock echo. Проверять семантические факты, границы и переходы. Существующие frozen-тесты не переписывать под желаемый ответ.

```sh
uv sync --frozen
uv run ruff check .
uv run pyright
uv run pytest tests/ --ignore=tests/test_frozen_snapshot.py --ignore=tests/test_golden_positions.py --ignore=tests/test_observability.py --ignore=tests/test_storage.py --ignore=tests/test_audit_models.py -p no:warnings

```

Исключённые DB-наборы не исчезают: для изменения persistence/recovery дополнительно поднять изолированную тестовую БД и прогнать соответствующие интеграционные тесты. Production БД не сбрасывать.

Артефакты `.audit_cache/`: evaluation manifest/hash references, результаты всех повторов, graph transition log, сравнение требований и доказательств, скриншоты и проверенный Word. Исторические отчёты не переписывать.

Порядок: 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7. Corpus tools и persistence можно разрабатывать независимо после фиксации внутренних contracts этапа 2; интеграционный владелец один.

Reviewable поставки:

1. Baseline и критерии; dependency/runtime smoke.
2. Доменные contracts и фактический evaluator.
3. Corpus API, инструменты и поиск.

## 17. Что требует решения до реализации

1. Подтвердить переход именно ядра на LangGraph, а не перепись приложения или мультиагентную команду.
2. Согласовать стандарт доказательств нормативных строк: действующий критерий PDF-ссылки для каждой строки нельзя выполнить честно, если соответствующего подтверждения в ПД нет.
3. Утвердить gold/holdout и стоимость/число разрешённых live-прогонов для сравнения. Старый стоп-критерий не снимается самим фактом смены библиотеки.
4. Подтвердить внутренние additive DB-миграции для checkpoints/ledger; frozen-контракты оставить неизменными.
5. При недостаточности текущего result DTO отдельно согласовать его расширение; иначе сохранять публичный контракт.
