# Разработка и проверки

Приложение запускается через Docker Compose; установка локальных инструментов ниже нужна для разработки и проверок, а не для рабочего развёртывания. Актуальные команды CI — в [`.github/workflows/ci.yml`](../.github/workflows/ci.yml). Результаты прошлых запусков и число прошедших тестов не гарантируют состояние текущего кода.

## Backend

Из `backend/` используйте Python из `.python-version` и зафиксированные зависимости:

```bash
uv sync --frozen
uv run ruff check .
uv run pyright
uv run pytest
```

Для полного набора CI использует отдельную PostgreSQL, `TEST_POSTGRES_URL`, Tesseract с языками `rus` и `eng`, а также установленные нормативные данные (`NORMATIVE_KB_ROOT`, `NORMATIVE_ROAD_KB_ROOT`); точная установка и переменные показаны в CI. **Тестовая БД должна быть отдельной и одноразовой:** тесты могут очищать данные; никогда не указывайте рабочую базу. Без внешних предпосылок возможны пропуски или ошибки, поэтому частичный прогон не равнозначен CI. Ruff format в CI проверяет только новые Python-файлы относительно базы изменения, а не переформатирует существующий код.

Для офлайн-baseline без реальной LLM, из `backend/`:

```bash
uv run pytest tests/test_baseline.py -v
uv run python tests/baseline_audit.py --output .audit_cache/baseline-dev
```

Baseline использует синтетические документы и подменный клиент; он не оценивает качество реального провайдера. Живой прогон отправляет данные провайдеру и расходует квоту, поэтому его выполняют отдельно и только с разрешёнными документами.

## Frontend и контракты

Установка, генерация OpenAPI/SDK, проверки Oxlint/Oxfmt/TypeScript, unit, build и Playwright описаны в [frontend/README.md](../frontend/README.md#контракты-и-проверки). Генерируемые файлы не правят вручную. При изменении backend DTO пересоздайте OpenAPI и клиент, затем проверьте актуальность контрактов. CI использует отдельную PostgreSQL и синтетический LLM-клиент для E2E; это не живой аудит и не доказательство качества модели.

## Проверка запущенного стека

`docker compose ps` показывает состояние контейнеров, `GET /healthz` — доступность API, но не проверяет весь пользовательский сценарий и модель. `backend/scripts/verify.sh` и `make verify` сейчас используют устаревший multipart `project` вместо обязательных `project_id` и назначения документа, ожидают отсутствие ключа LLM, перезапускают API и создают резервную копию; не используйте их как надёжную или безвредную проверку актуального стека. Для ручной проверки используйте изолированный проект и API-контракты из [api.md](api.md), не настоящие документы без разрешения.
