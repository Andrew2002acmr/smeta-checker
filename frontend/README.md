# КДФП · Nuxt workspace для smeta-checker

Nuxt 4 / Vue 3 / TypeScript / Nuxt UI. Этот интерфейс работает с `backend/api.py` в этом же репозитории: `/api/v1`, постоянные проекты/версии/audit runs, Celery либо существующий fallback.

## Запуск

```powershell
Copy-Item .env.example .env   # заполнить POSTGRES_PASSWORD, AUDIT_API_TOKEN, WORKSPACE_LOGIN, WORKSPACE_PASSWORD
docker compose up -d --build
```

Интерфейс: **http://127.0.0.1:3000**, API: **http://localhost:8000**.
Нативный запуск без Docker не поддерживается.

Development frontend: задайте серверные `NUXT_BACKEND_URL` и `NUXT_BACKEND_TOKEN`,
затем `pnpm --dir frontend dev`. Токен нельзя переносить в `runtimeConfig.public`,
браузерное хранилище или `NUXT_PUBLIC_*`.

## Пользовательский цикл

Главная (`/`): список постоянных проектов с поиском по проекту или ведомости,
сортировкой и вкладками «Активные» / «Архив». Строка открывает проект, а не
последний запуск. Название задаётся вручную; автоматического AI-именования нет.
Переименование не меняет UUID и ссылки.

В строке показаны количество ВОР, PDF и проверок, дата и ведомость последней
проверки, затем результат по позициям. Цветом выделены только результаты,
а не название проекта. Завершённая проверка без доступной сводки показывает
«Результат недоступен» с отдельным повтором загрузки, а не нулевые замечания.
Отсутствие проверок не означает, что документы не загружены.
На телефоне те же сведения располагаются последовательно под названием,
без горизонтальной прокрутки таблицы.

Переименование и архивирование находятся в меню «⋯» строки; архивирование
требует подтверждения. В архиве через это меню доступно восстановление.
Кнопка «Новый проект» находится рядом с заголовком списка проектов; в общей
шапке и пустом состоянии она не дублируется. Загрузка показывает скелетон
строк, ошибка списка и отсутствие результатов поиска имеют отдельные
состояния с повтором или сбросом поиска.

Архив открывается по `/?archived=true`; вкладки доступны и при пустом списке
или ошибке загрузки. Логотип и «Проекты» в шапке возвращают на `/` к активным
проектам. Кнопка «Назад» браузера восстанавливает просмотр архива.

1. «Новый проект» → название → «Создать проект». Внутри проекта — вкладки
   «Ведомости», «ПД» и «Проверки».
2. «Добавить документы» принимает несколько XLSX/CSV/PDF, папки с вложенностью
   через drag&drop или системный диалог. Пределы: 50 файлов, 100 МБ на файл.
   Перед сохранением для каждого файла явно выберите отдельный документ либо
   новую редакцию существующего. Совпадение имени не объединяет документы.
3. В карточке ведомости доступны реквизиты с источником (лист/ячейка), ручные
   уточнения, редакции и история проверок. Реквизиты извлекаются без OCR и
   LLM; неоднозначные поля остаются пустыми. Исходное извлечение и ручные
   уточнения хранятся раздельно.
4. «Проверить» выполняет preflight и запускает проверку по действующим
   редакциям всех проектных PDF — выбирать и подтверждать привязку не нужно.
   Обозначения из колонки «Ссылка на чертежи» сверяются с текстом ПД:
   отсутствующее обозначение даёт позиции статус «Ошибка» без вызова модели.
   При критических ошибках preflight требуется явное подтверждение, затем
   повторное нажатие. Каждая проверка — новый запуск со снимком конкретных
   редакций ВОР и ПД.
5. Новая ВОР сохраняет UUID ведомости даже при другом имени файла. Повтор тех
   же байтов в одном документе использует ту же редакцию. Новая ПД не
   подменяет действующую: выберите её явно кнопкой «Сделать действующей».
   Старые результаты, доказательства и Word продолжают открываться по прежним
   источникам.
6. Архив скрывает проект/документ без удаления; восстановление проекта не
   восстанавливает отдельно архивированные документы. Редакции, использованные
   в проверках, защищены от физического удаления. Проект в архиве можно
   удалить навсегда кнопкой «Удалить» с вводом названия для подтверждения —
   документы, проверки и результаты стираются безвозвратно.
7. Результаты содержат очереди, поиск/пагинацию, Word-отчёт и окно сверки.
   Excel-отчёта и ввода пути к папке нет; исходный XLSX можно скачать.
   В сверке PDF-навигация независима от вердикта; переход страницы не подтверждает
   позицию. На телефоне доступны отдельные вкладки ВОР и PDF.
   Имя исходной ведомости показано один раз: без суффикса копии `(1)` и с пробелами
   вместо подчёркиваний. Длинное имя сокращается в середине, полное доступно в `title`.
   Статус запуска показан бейджем, счётчики — в фильтрах очередей.
8. Светлая и тёмная темы переключаются кнопкой в шапке. Общие семантические токены находятся в `app/assets/css/theme.css`; эталон экранов — pen.dev, см. корневой `AGENTS.md`.

Проверка оформления вызывается для первого листа XLSX (или выбранного из списка), без LLM. Замечания сгруппированы по смыслу с фильтром и поиском; соответствие запоминается на ревизии и показывается бейджем. Из карточки ведомости скачиваются Excel с подсвеченными ячейками и Word-отчёт для внешних проверяющих. Кнопка «Проверить ВОР» в шапке приложения проверяет любой файл без сохранения. CSV не выдаётся за редактируемую книгу Excel. ONLYOFFICE, сохранение редакторских ревизий и PDF-заметки в этой версии интеграции ещё не подключены.

## Контракты и проверки

```powershell
cd backend; python -m scripts.export_frontend_openapi; cd ..
pnpm --dir frontend run api:generate
pnpm --dir frontend run api:check
pnpm --dir frontend run fmt:check
pnpm --dir frontend run lint
pnpm --dir frontend run typecheck
pnpm --dir frontend run test:unit
pnpm --dir frontend run build
```

Источник схем — реальные Pydantic DTO в `backend/workspace_models.py`, `backend/audit_models.py` и `backend/api.py`. Сгенерированный SDK/TS/Zod находится в `app/generated/`; вручную его не редактируют. Экспорт OpenAPI не открывает БД и не запускает OCR/LLM.

Unit-тесты чистых функций и контрактов выполняются в Node, без запуска Nuxt. Пользовательские сценарии и компоненты проверяются E2E на собранном приложении.

Для E2E используется отдельная PostgreSQL `smeta_test_ui`, `backend/tests/workspace_server.py`, синтетические файлы и явно подменный тестовый LLM-клиент. Это испытание интеграции, не живой прогон модели. Начальный запуск требует пустую БД и новый `--root`; `--resume` использует уже созданный тестовый комплект без удаления данных. Обычный production entry point тестовый клиент не подключает.

После запуска fixture API на 8116 и built Nuxt на 3016 задайте `FRONTEND_URL=http://127.0.0.1:3016` и `E2E_FIXTURE_ROOT=<полный путь fixture>`, затем `pnpm --dir frontend run test:e2e`. В окружении приложения и раннера тестов задайте `WORKSPACE_AUTH_MODE=local` с тестовыми `WORKSPACE_LOGIN`/`WORKSPACE_PASSWORD` (синтетические значения, без секретов). GitHub Actions содержит эти шаги с отдельной тестовой БД.

Для полного синтетического комплекта после готовности API выполните
`backend/tests/table_layout_fixture.py <root>` и
`backend/tests/progressive_fixture.py seed <root>` тем же Python и с той же
`TEST_POSTGRES_URL`. Для progressive-теста также задайте `E2E_PYTHON` (полный путь
к Python). PDF для выделения и OCR создаются самим `workspace_server.py`;
OCR-тест требует установленного Tesseract с языками rus и eng.

Тесты `normative-pilot`, `normative-context` и `normative-position-check`
требуют внешнего нормативного выпуска и соответствующего тестового профиля API.
Запускайте их отдельно с `E2E_NORMATIVE_PROFILE=electrical` или `roads` и
`workspace_server.py --normative-profile <профиль>`. Без этого они явно пропускаются:
корпуса и PDF нормативов не входят в checkout, а эти сценарии читают реальные
нормативы и сохранённый результат предыдущего шага. Остальные браузерные тесты
работают на синтетических данных без нормативного корпуса.

E2E выполняет вход один раз в `tests/e2e/setup.ts`, передаёт синтетическую
сессию worker-процессам только через окружение и отзывает её после прогона.
Перезапуск worker после ошибки не расходует новые попытки входа.

## Как устроен запуск и переключение режимов

Nuxt входит в общий `compose.yaml` как сервис `workspace`. Порт публикуется только
на host loopback (`127.0.0.1:3000`); Python-токен остаётся только у BFF.
В Compose серверные сессии хранятся в Redis DB 1; без Redis локальный стенд
использует память процесса. Старые подписанные cookie больше не принимаются.

Вход обязателен везде, анонимного доступа нет. `WORKSPACE_AUTH_MODE` принимает
ровно два значения: `local` (по умолчанию, пустое — тоже `local`) и `ldap`.
В режиме local вход — по паре `WORKSPACE_LOGIN` + `WORKSPACE_PASSWORD` из `.env`
(оба обязательны): логин чувствителен к регистру (пробелы по краям
отбрасываются), пароль сравнивается точно. Без обоих значений вход отвечает
503, неверный или пустой логин/пароль — общий 401. Лимиты входа — 3 попытки на
учётную запись и 20 с IP за 15 минут, включая успешные попытки; LDAP-вызовы
в local не выполняются. Учётная запись сессии — настроенный `WORKSPACE_LOGIN`;
параметры `LDAP_*` в этом режиме игнорируются. `WORKSPACE_AUTH_MODE=ldap`
заменяет локальную пару корпоративным входом через серверный `ldapts`; требует
Redis, `WORKSPACE_ORIGIN` (HTTPS) и подтверждённых параметров AD. Политика
авторизации — `LDAP_ACCESS_MODE` (пусто = `group`, безопасное значение
по умолчанию): `group` требует полный `LDAP_GROUP_DN` и пускает только членов
этой группы с учётом вложенных групп AD; `all` пускает любую
активную/разблокированную/неистёкшую учётную запись-пользователя в
`LDAP_BASE_DN`, кроме служебной записи поиска (роли сотрудников не выводятся,
прочие служебные записи с верным паролем тоже проходят). Пустой
`LDAP_GROUP_DN` — не «все»: в `group` он обязателен, в `all` игнорируется
(оставьте пустым). Для `all` нужен полный DN в `LDAP_BIND_DN`
(`CN=smeta,CN=Users,DC=kdfp,DC=ru`), не UPN/короткое имя; в `group`
допустимы полный DN и UPN. Пустой `LDAP_TLS_MODE` = безопасно по умолчанию
(`ldaps://` → LDAPS, `ldap://` → обязательный STARTTLS до обоих bind); явный
`LDAP_TLS_MODE=none` — только для `ldap://` как сознательный opt-in внутренней
сети (как Bitrix): пароли служебной записи и сотрудника идут незашифрованными
на участке ПК/сервер → AD. Режимов входа по-прежнему два, проверки
цепочки/имени не отключаются, ошибка TLS никогда не откатывается в `none`.
Опечатка в режиме — 503, недоступность AD в режиме ldap — 503 без fallback
на local. Все API и файлы защищены одной проверкой сессии, страницы —
middleware. В шапке доступен выход с удалением серверной сессии. Сессии
перепроверяются каждые 5 минут: отзыв/отключение в AD запрещает следующий
запрос, выход удаляет серверную сессию. Это общее рабочее пространство
(в `group` — разрешённой группы), не система ролей/изоляции проектов;
базы пользователей и регистрации нет.

Настройка `.env`, read-only CA и команды пересоздания workspace:
[инструкция Docker](../docs/docker-quickstart.md#вход-два-режима-без-анонимного-доступа).
Production без отдельной команды не переключать.

Проверка двух режимов 2026-10-23: 68 unit-тестов, 10 E2E на отдельной БД
с синтетическим LLM-клиентом, typecheck/lint/форматирование/OpenAPI,
сборка Nuxt и Docker — успешно. В браузере проверены обе формы,
локальный вход → исходная защищённая страница → выход → повторный запрос входа.
LDAP-режим с доступными локальными данными при недоступности AD возвращает
503 без сессии. Подтверждены IP AD `192.168.30.200`, DNS-имя
`kdfp-dc1.kdfp.ru`, домен `kdfp.ru`, `DC=kdfp,DC=ru`; разовый bind записи
`smeta` успешен (DN `CN=smeta,CN=Users,DC=kdfp,DC=ru`, UPN `smeta@kdfp.ru`,
ровно один результат поиска). Живые STARTTLS (ошибка 52) и LDAPS (сброс)
ранее неуспешны; вход сотрудника и авторизация по группе/всем не тестировались.
Запись `smeta` — только поиск, прав администратора не требует.

Проверка явного `LDAP_TLS_MODE=none` (2026-10-23): 76 unit-тестов,
typecheck/lint/форматирование/OpenAPI и сборки Nuxt/Docker — успешно.
Из одноразового Docker-контейнера через SSH/Tailscale → рабочий ПК → AD
выполнены реальный служебный bind и поиск: найден ровно один пользователь `smeta`.
Сам модуль `checkLdapAccess` проверен на реальном AD: безопасный режим по умолчанию
отказывает при ошибке STARTTLS, явный `none` читает статус и отказывает для
переданного в отрицательной пробе DN пользователя вместо группы.
Это не приёмка входа сотрудника: тестовая учётная запись сотрудника ещё нужна
(для `group` — также `LDAP_GROUP_DN`). Production и рабочий `.env` не изменялись.

Политика `LDAP_ACCESS_MODE=all` (2026-10-23): 90 unit-тестов,
typecheck/lint/форматирование, Compose config и production-сборка Nuxt/Docker —
успешно. На реальном AD через SSH/Tailscale из Node и Docker подтверждены:
доступ активной записи без группы, запрет служебной записи (алиасы логина,
эквивалентные DN), повторная проверка группы после переключения на `group`,
отказ при пустой группе в `group` и неизвестной политике.
В собранном Nuxt-контейнере с отдельным Redis проверены 401 для API/скачивания
без сессии, пустого пароля и входа служебной записи, без выдачи cookie.
HTTP smoke выполнен на loopback с точным raw Host/Origin; публичный HTTPS
и вход сотрудника с паролем → защищённая страница → выход не проверены.
Секреты/имена сотрудников в отчёт не сохранялись; рабочий `.env` и production
не изменялись. Артефакт: `.audit_cache/all-access-verification.json`.

Интеграция релиза с серверными хотфиксами (2026-10-23): сохранены исправления
поиска по кандидатам, нумерации листов тома и frozen snapshot. Старый механизм
продления подписанной cookie и его тест удалены при переходе на серверные сессии.
LDAP mock сессий закреплён одной фабрикой: динамическая пара unmock/mock
могла недетерминированно подставить реальный LDAP-клиент в unit-тест.
Устаревший тест внутреннего DataFrame-возврата отчёта удалён; содержимое
отчётов проверяется через API. На отдельной БД: 509 backend-тестов и 90
frontend unit-тестов, ruff/pyright/typecheck/lint/OpenAPI — успешно.
На собранном Nuxt выполнены 10 E2E с отдельной PostgreSQL и синтетическим
LLM-клиентом: вход, API, загрузка, результаты, PDF и Word-экспорт.

### Проверка зависимостей (2026-10-22)

`pnpm audit --prod` сообщает две high без опубликованного исправления:
[`node-forge`, GHSA-86w9-cpqp-85rv](https://github.com/advisories/GHSA-86w9-cpqp-85rv)
через dev-server `listhen` и
[`braces`, GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
через build-time `globby/micromatch`. Также есть low
[`esbuild`, GHSA-g7r4-m6w7-qqqr](https://github.com/advisories/GHSA-g7r4-m6w7-qqqr)
в ветке `@nuxt/fonts` (dev-server Windows).
Эти пакеты отсутствуют в manifest/node_modules готового `.output/server`
и не импортируются серверными `.mjs`; Docker runtime копирует только `.output`
и скрипт приёмки, не зависимости сборщика. Для LDAP TLS используется `node:tls`,
не `node-forge`. Отложено обновление upstream Nuxt/build-chain, без принудительных
overrides: сборка выполняется только из доверенного исходного кода; dev-server
не публиковать. Перепроверить advisories не позднее **2026-11-05** и перед релизом.
